# Ollama bench results

Local benchmark of installed Ollama models against real projects in
`~/Projects/orgs`. Generated by [`scripts/bench-ollama.ts`](../bench-ollama.ts).

## 2026-05-13 — installed-only run (n=12 projects)

After alias-aware scoring (PostgreSQL→pg, Telegram→grammy/telegraf, etc),
package.json `keywords` added to ground truth, and Ollama `response_format:
json_object` mode enabled in OllamaAdapter:

| model              | runs    | ok      | json valid | mean latency | median latency | mean gt-score |
|--------------------|---------|---------|------------|--------------|----------------|---------------|
| **qwen2.5-coder:3b** | 12/12 | 12/12   | 12/12      | 9.0s         | 9.6s           | **95%**       |
| llama3.2:latest    | 12/12   | 12/12   | 12/12      | 12.4s        | 12.9s          | 89%           |
| gemma3:1b          | 12/12   | 12/12   | 12/12      | **4.7s**     | 4.7s           | 86%           |

JSON mode adds ~2s/call on qwen2.5-coder:3b but guarantees parseable JSON —
eliminates rare malformed-output failures we used to handle via regex extraction.
gemma3:1b speed *improved* (5.3 → 4.7s) because grammar-constrained decoding
prevents wasted tokens on prose preamble.

### Agent-loop POC (option C)

`scripts/bench-agent.ts` runs a Claude-style agent loop: model gets sandboxed
read-only tools (`list_dir`, `read_file`, `grep`) and decides what to explore
before producing the JSON. Findings on 16GB M1:

| model              | tool path                       | quality on `agent-cv` | tool calls | latency |
|--------------------|---------------------------------|-----------------------|------------|---------|
| qwen3:0.6b         | ignores tools, fabricates       | trash                 | 0          | 5.7s    |
| **qwen2.5-coder:3b** | inline-parser fallback        | **accurate, 9 deps**  | 8          | **25s** |
| llama3.2:latest    | native Ollama tool_calls       | accurate, 6 deps      | 5          | 34s     |
| mistral:latest     | ignores tools                   | n/a                   | 0          | n/a     |

**Key win**: the inline parser ([scripts/bench-agent.ts](../bench-agent.ts) `parseInlineToolCalls`)
extracts tool calls from models that emit them as `{"name": ..., "arguments": ...}` in
content instead of via Ollama's structured `tool_calls` field. This makes our existing
default `qwen2.5-coder:3b` (1.9GB, no extra disk) viable for agent loops.

Agent loop **wins on monorepo / under-documented projects**. Example: `alerts`
where single-shot returned `["TypeScript", "Telegram Bot API"]` (50% gt), agent
loop returned `["typescript", "tsup", "vitest", "typescript-eslint"]` (real deps)
plus contributions referencing actual code symbols (`AlertClient`, `createTelegramTransport`)
because the model read the source.

But agent loop is **3× slower** than single-shot. For 600-project batches:

- Single-shot qwen2.5-coder:3b: ~80 min serial
- Agent loop qwen2.5-coder:3b: ~250 min serial (~4 hours)

Default stays single-shot. Use `bun run bench:agent --project <path>` for
deep-dive on individual projects where quality matters more than batch speed.

### Concurrency reality check

Local Ollama serializes requests on a single loaded model instance, so the pipeline's
default `AGENT_CV_CONCURRENCY=8` does not actually parallelize Ollama calls — it
just queues them. OllamaAdapter now reports `maxConcurrency = 1` (or `OLLAMA_NUM_PARALLEL`
if set) and the pipeline respects that.

**Realistic wall-clock for 600 projects** with default qwen2.5-coder:3b + JSON mode:

- Default serial: 600 × 9.6s ≈ **96 min**
- With `OLLAMA_NUM_PARALLEL=4` on ollama daemon: ≈ **24 min**
- Swap to gemma3:1b (4.7s/proj, 86% gt): serial ≈ **47 min**, with parallel=4 ≈ **12 min**

To enable parallel Ollama inference, set `OLLAMA_NUM_PARALLEL` before starting
the ollama daemon (or in the Ollama app's env):

```bash
launchctl setenv OLLAMA_NUM_PARALLEL 4
# restart Ollama.app
```

**gt-score** = jaccard of returned `techStack` against signals extracted from
project manifests (`package.json` deps + keywords, Cargo.toml, pyproject.toml
both PEP-621 and Poetry forms, requirements.txt, go.mod, Anchor.toml) plus a
tech-alias map for common name mismatches.

### Verdict — `qwen2.5-coder:3b` stays default

- 95% accuracy beats both faster (gemma3:1b at 82%) and slower (llama3.2 at 89%) options
- 1.6× faster than llama3.2; only ~40% slower than tiny gemma3:1b but +13pp accuracy
- 1.9GB on-disk and good 16GB-RAM concurrency profile

### Per-stack observations

- Rust projects (`screen-studio-polyrecorder-*`): qwen2.5-coder:3b nails cpal/ffmpeg/tokio/tauri
- Python projects (`pwnagotchi`, `Open-Interface`, `earning-protocol-model`): 96-100% on real deps
- TS monorepos (`backend`, `alerts`): occasional alias misses (Telegram Bot API vs grammy)
- Solana (`spool-hq`): correctly returns Rust/Solana/Anchor

### Not benchmarked (no disk space)

User had 6GB free at bench time; bigger pulls aborted to avoid disk pressure.
Listed in `PREFERRED_OLLAMA_MODELS` so auto-detect picks them up once pulled:

- `qwen3.5:4b` (~2.5GB) — public benchmarks claim +10-20pt on coding (May 2026)
- `gemma4:e4b` (~9.6GB) — native tool calling + 128k context
- `ministral-3:3b` (~1.8GB) — Mistral edge-tuned JSON / function calling

To upgrade default once disk allows:
```bash
ollama pull qwen3.5:4b
bun scripts/bench-ollama.ts --models qwen2.5-coder:3b,qwen3.5:4b \
  --root ~/Projects/orgs --pick 20
# If qwen3.5:4b shows >5pp accuracy win, swap RECOMMENDED_OLLAMA_MODEL in
# packages/core/src/analysis/adapters/ollama-adapter.ts
```

## Reproducing

```bash
# Bench installed models on 12 diverse projects under ~/Projects/orgs:
bun scripts/bench-ollama.ts \
  --models qwen2.5-coder:3b,llama3.2:latest,gemma3:1b \
  --root ~/Projects/orgs --pick 12

# Explicit projects:
bun scripts/bench-ollama.ts \
  --models qwen2.5-coder:3b \
  --projects ~/Projects/orgs/agent-cv/agent-cv,~/Projects/orgs/spool-hq

# Add new model: pass --pull to fetch missing tags first.
bun scripts/bench-ollama.ts --models qwen3.5:4b --pull \
  --root ~/Projects/orgs --pick 10
```

Each run writes raw JSON to `/tmp/bench-ollama-<timestamp>.json`. The latest
trustworthy run is saved alongside this README as `bench-ollama-local.json`.
